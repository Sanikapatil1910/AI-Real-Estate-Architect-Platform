# Smart House WebXR — test report (final, after the requirements review and the walkability / accessibility work)

Three layers, kept separate. **Nothing here was run on a Meta Quest 2, and no Quest compatibility, frame rate (72/90 Hz), comfort or controller-mapping claim is made.**

Environment of every run below: Linux container, Node 22, headless Chromium with software GL (SwiftShader), real FastAPI backend (temporary SQLite DB), real Vite dev server. No GPU, no headset.

### 1b. Node audits over generated plans (executed)

* 89 plans: 21 stored fixtures + 16 + 52 freshly generated by the backend `/generate` (1–3 floors, Modern / Traditional / Wada, plots 25×40 to 60×80, all four road sides, Vastu on/off, setbacks 0–6 ft). Generator inputs of the 52: `frontend-react/dev/fixtures/gen2_*.json` (`tools/generate_audit_layouts.py`, fixed seed; audit: `frontend-react/dev/audit_access.cjs`, report: `tools/access_report.py`).
* Reachability on foot: see `docs/VR_ACCESSIBILITY_REPORT.md` — strict audit from OUTSIDE the front door over 89 layouts (21 stored + 16 + 52 freshly generated): **89 / 89 layouts reach every room, every plan door and every floor on foot; 0 unreachable rooms** (previous build: 29 / 89; 148 rooms unreachable from the start point). Go G / Go 1F / GO buttons and teleport remain as extras, not as the way in.
* Teleport audit over all 21 fixtures: 0 landings that were not standable, 0 landings off a floor level or stair surface, no tunnelling through a slab inside the footprint; cross-floor and stair landings present.
* Seat audit: 325 seats over the 21 fixtures, all with a measured seat height and a stand spot. **3 freshly generated 3-floor Traditional/Modern houses have a dining room with no chairs** (the generator placed no table there) — there is nothing to sit on in those rooms.

### 1c. Browser end-to-end, 8 houses (real pages, real key/mouse events)

Houses: `g1_0`, `g2_0`, `sc_g2` (older samples) and five freshly generated plans (`fresh_30x40_g`, `fresh_40x60_g2_vastu`, `fresh_25x45_g1_wada`, `fresh_50x70_g1_garden`, `fresh_45x55_g2_terrace`).
**Result of the complete re-run after the walkability changes: 224 / 224 desktop checks (28 per house), all 8 houses 28/28, in one pass without any re-run.**

Per house (28 checks): list page + Enter VR button · viewer opens the right house · house built → `.glb` header checked → loaded back → merged · smart-house data matches the plan · no headset → Enter VR disabled with reason, desktop walk works · start on a floor surface · W/S/arrow walking, wall stops · panel all on/off, single light, fan − / + 0..5 · fan blade speed measured on the scene objects · automatic lighting incl. manual override and off-after-delay · **motion lighting in every bedroom and on every stair flight** · **cross-route sync** (panel / typed command / wall switch / wall regulator) · energy panel labelled *Simulated* · wall plate clicks · rendering brighter with lights on · typed command · floor buttons · **teleport (hold T; wall/ceiling refused; upper floor)** · **sit / stand (E; panel SIT NEAREST / STAND UP; walking stands up)** · voice absent → clear message, manual controls work · no uncaught page errors.

Test-harness notes (from the earlier run, before the walkability work; the re-run above needed none of these fixes): the first pass over 8 houses showed 3 failing houses. Each was a test-hygiene problem, not an engine defect, and was fixed in the test only: (1) on single-floor houses the floor-button test skips its click, so focus stayed in the typed-command box and T/E keys went to the box as designed — the test now leaves the box; (2) the control panel stayed open from the previous check and (as designed) took the trigger instead of a sofa disc behind it — the test now closes it; (3) the 5 s wait for "mode back to desktop" after EXIT VR was too short on the slow software-GL browser (the engine had already logged "Left VR") — wait raised to 20 s. The two affected houses were then re-run completely (28/28 and 7/7). The other 6 houses had their last full run on the previous harness revision, which differs only in those three lines.

Software GL → **no frame rate is reported.**

## 2. Simulated WebXR (labelled MOCK in the test names) — 56 / 56 (7 per house, 8 houses, re-run after the walkability changes)

A fake `navigator.xr` + fake session (the real `setSession` replaced by a no-op) with injected input. These prove our code reacts correctly to the values a Quest *should* report, **not** that the Quest reports them.

1. availability check reports supported → Enter VR enabled
2. Enter VR requests `immersive-vr` with `local-floor`/`bounded-floor`; VR mode, panel closed; Exit VR returns to desktop
3. injected left-stick push walks forward through the collision grid; injected right-stick flick snap-turns 30° once
4. **injected right-stick forward aims the teleport arc (arc + marker); release teleports with a blink, standable at the target; pulling back cancels**
5. injected Y button opens the panel ~1 m in front; injected trigger on a posed controller presses ALL LIGHTS ON / OFF and EXIT VR
6. injected trigger on a wall switch plate toggles the light
7. **injected trigger on a sit disc sits (eyes ~75 cm above the seat), left-stick push stands up; panel STAND UP works; sitting again re-sets the height**

## Known limitations (found by these tests)

* Walkability limits found by the audit (details in `docs/VR_ACCESSIBILITY_REPORT.md`): 7 older stored sample plans (33 rooms) are walkable only THROUGH a bathroom, bedroom, balcony or terrace — the backend circulation rules reject those plans and they should be regenerated; the walking model also adds doors where an uploaded plan has none (marked, reported); one tight bedroom (`pk_g1`, first floor, three doors in 10 × 13 ft) is left without a bed to keep its doorways clear.
* Some generated dining rooms have no table and no chairs, so there is nothing to sit on there.
* Teleport needs a line of sight: an arc cannot go through a wall or ceiling; a stairwell can be used for cross-floor landings only when the arc can reach it.
* Furniture heights for sitting are read from the mesh; unusual furniture shapes may give a slightly off seat height (eyes are always placed 75 cm above the measured seat, and "SIT" again re-calibrates).
